**RATIFIED 2026-06-22 (Option A).** Build ONE unified, deterministic, stitch-accurate finished-object render engine ("the loom"), as its own orchestrator-owned workstream. Every pattern craft (cross-stitch, needlework, crochet, knitting, sewing) renders its heroes through it. It is the spine of the Studio + the independent-designer/marketplace business model. Crochet + needlework sign-offs both hit the same hero wall independently; this solves it ONCE instead of four parallel render stacks each re-solving accuracy.

## CANONICAL PROCESS — WRITTEN DOWN 2026-06-24 (the fix for sessions re-deriving + improvising the steps)
The pattern→hero process is now a committed repo doc: **`apps/web/src/lib/loom/RENDER_PROCESS.md`** (on main, commit 824db562). Every render session follows it exactly; point each session at it. Two phases: **Phase A** (VARIES per pattern, done BEFORE the render session, never its job) = get the pattern INTO our format (per-element geometry + stitch-dictionary slug + DMC colour); read every element, never guess, never infer a stitch from a shape (that turned Countryside into a "knot meadow"), extract vector geometry never rasterise-and-trace. **Phase B** (ALWAYS IDENTICAL) = Step 3 VALIDATE (overlay the our-format line-art on the original line drawing, must match exactly, never render unverified) → Step 4 RENDER (exact stitches → Blender path-trace → locked Fal upscale → fidelity gate → photo + document from the same data). Independent-designer onboarding will later automate Phase A. Root cause it fixes: the steps lived only in chat, got lost each session → unfaithful renders. ALSO NOTED: the `countryside.final-c05.png` "approved" render is NOT actually faithful (poppies render as orange daisies not solid shaded red; asters tiny not pink-spiky) — "THAT IS SOLVED" was overstated; we do NOT yet have a faithful Countryside hero.

## The core principle (why it's "one engine")
The render is a DETERMINISTIC function of the pattern's COMPLETE structured stitch data — accurate by construction, never invented, exactly like the cross-stitch grid renderer (which works because cross-stitch fabric IS a flat regular grid, so grid-of-cells maps 1:1 to reality). To get that guarantee everywhere, every craft's pattern must carry full machine-renderable structure: crochet = the stitch graph; needlework = region + thread-direction + stitch-type map; sewing = panel + seam geometry. Not just prose + a symbol chart.

## Three tiers behind one shared interface (split by dimensionality, NOT by craft)
- **Tier 1 — grid render:** cross-stitch + counted needlework. Already works; WRAP it, don't rebuild.
- **Tier 2 — 2D structural render:** free-form needlework (thread-stroke region fill) + flat crochet/knit (loop-geometry fabric).
- **Tier 3 — 3D constructed render:** amigurumi, crochet/knit garments, sewn garments. Heaviest tier; gates showpiece/whimsical content, amigurumi and ALL garments across crafts.

## The quality bar (this is the hard part, not the theory)
Accurate AND it must LOOK like a real tester stitched it. Past renders failed on exactly this: either unfaithful to the stitches, or accurate-but-weird-looking. The existing crochet 2D vector renderer (per-stitch rim/body/sheen strokes) is BAD — don't reuse it, it produced the weird results. Floor = **render-grade-accurate** (a clean studio render of the real object, good yarn/thread shading). Photographic LIFESTYLE heroes come only from real makers/designers later; an optional staging layer could composite the truthful render into a scene WITHOUT ever faking stitches. AI lifestyle images are technically possible but NOT required (real users will make them). **img2img is REJECTED** — it produces beautiful images that ignore the actual stitches (the needlework moth is the proof). No AI image gen, no paid APIs ([[feedback_no_api_spend]], [[feedback_image_strategy]]).

## The four per-pattern deliverables (the goal of the whole system)
Every pattern, from ONE Studio document model: (1) makeable instructions, (2) symbol/stitch chart, (3) line drawing (a schematic with dimensions for garments; line art for many items), (4) render-grade finished-object hero. We already have the symbol chart + the US/UK toggle, which most peer sites lack.

## Studio + independent-designer dependency (this forces the architecture)
The engine's INPUT is the Studio's structured document model. The render runs on-demand and IDENTICALLY for Homemade-authored and user-authored patterns. A user designs in the Studio → gets the same hero quality → registers as an independent designer → sells on Homemade. So this is the literal foundation of the creator/marketplace model, not a cosmetic content task. Four separate renderers can't deliver that; one engine with craft adapters can.

## Three-layer boundary — RATIFIED 2026-06-22 (the loom is RENDER-ONLY)
Three layers, not two. Keep them separate so the loom stays lean and shared:
1. **Brief (what to make)** — the shared design-direction system (`design-direction.ts`): Territory × Look × Item-type × Palette + a hook. Shared across all crafts ([[project_cross_craft_design_direction]]).
2. **Generation (brief → structured stitch data)** — CRAFT-SPECIFIC, owned by each craft/category, built in their own sessions. Generating a blackwork chart vs a needlepoint canvas vs a free-form line-art-with-stitch-assignments are different jobs; each craft/discipline has its own generator. Multiple producers feed the same contract: our craft generators, a user designing in the Studio, and the "design your own" create-your-own tools.
3. **Render (structured data → finished picture / template / legend)** — THE LOOM. Render-only. It renders whatever it's handed, identically for every producer. It does NOT invent or generate designs.
The structured-data contract is the join between (2) and (3). Putting generation INTO the loom would balloon it into "knows how to design blackwork AND needlepoint AND free-form AND crochet AND…" — the four-stacks mess we're avoiding. So: loom = render only; design generation = craft-owned, feeding the loom via the contract.

**Seamless for users:** the boundary is INTERNAL, not a user-facing seam. A user designing in the Studio edits the shared structured document live and the loom renders it live; they never walk through "generate" then "render" as steps. The "generation in its own session" framing applies ONLY to our offline BULK authoring (no user, no Studio). Seamlessness comes from the Studio editing the contract + the loom rendering fast/incrementally — which is the argument FOR render-only (co-locating wouldn't help, and would bloat it). Keep render real-time so the Studio preview stays instant.

**Standing principle for ALL future categories, incl. non-fibre (added 2026-06-22).** This boundary holds for every craft/project category, not just the fibre crafts. Woodwork projects (cut lists, joinery, a render of the finished piece), paper craft (templates), and others will all want tutorials + patterns/plans. The loom is the shared RENDER spine and WILL extend further than first scoped; each new craft adds its own GENERATION (brief → structured data) plus a render adapter/tier, and feeds the loom via the contract. Design the loom + the structured-data contract to extend. Every future category sign-off inherits this: the category owns its generation; the loom renders.

## Stitch illustration scope — the loom owns ALL stitch drawing, including teaching diagrams (2026-06-22)
Decision: the loom owns the canonical stitch primitives (per-stitch geometry / needle-path), the single source of truth. Two output modes off the SAME primitives: (1) finished-fill (heroes / Tier-2 fabric), (2) teaching needle-path how-to diagrams (numbered steps, arrows, house line-style). The needlework STITCH library's ~91 embroidery how-to diagrams are a THIN consumer of the loom's primitives in teaching mode — NOT a fourth render stack with its own stitch definitions. Same fidelity bar as heroes (accurate by construction, no Fal — a wrong diagram teaches the wrong stitch). Composites that don't parameterise: trace-PD-and-redraw in the house line-style. Sequencing: the loom session establishes the primitives + the needle-path output mode; the bulk 91-diagram generation is a thin follow-on off them. Needlework proceeds text-first meanwhile (not blocking). Same principle covers future crochet/knit stitch how-tos.

## GATING RULE (how categories continue while the engine is built)
The engine gates a category going **COMPLETE / best-in-category / fully public-polished**, NOT the content build. BUT patterns built in the meantime MUST carry **complete structured stitch data** (Studio-makeable, real stitches, symbol chart, line drawing where needed). NO EMPTY SHELLS — the past failure was patterns with nothing in the Studio and no stitches. Interim library card = the chart / line drawing; the render-grade hero backfills when the engine lands. So content proceeds NOW to a higher bar; no category goes fully public-polished without truthful heroes; none sit idle waiting.

## RESET 2026-06-23 — pivot to embroidery-first, 2.5D thread rendering (the crochet 3D Blender path is a dead model)
The long crochet session got a jellyfish acceptable but STALLED on the fairy: washed-out, stitches not matching, bits cut off, not cute — Rebecca would not ship either. The 3D Blender path-traced amigurumi approach is REJECTED as the starting model (too hard, doesn't converge, doesn't scale, per-object hand-tuning). Pivot, with Rebecca's lead:
- **Embroidery FIRST** (flat 2D — same family as the WORKING cross-stitch renderer; far better odds of exact-stitch fidelity). Rebecca supplies two licensed embroidery patterns (simple + complex) as internal fixtures only (never shipped/sold/redistributed).
- **2.5D thread-stroke rendering, NOT 3D Blender** — each stitch is a real shaded thread stroke on fabric. Proven precedent: machine-embroidery DIGITIZING software (e.g. open-source **Ink/Stitch**, plus Wilcom/Embird) renders realistic stitch previews from stitch data — study the technique, don't vendor it. This is the "the right approach exists, far more complex software does this" point.
- **STITCH LIBRARY FIRST** (was NOT in the prior brief): build each embroidery stitch (satin, long-and-short, stem, back, chain, lazy daisy, French knot, couching, seed, fishbone…) as a deterministic accurate primitive; LOOK at each rendered against a real reference of that stitch and iterate until it's right, BEFORE any pattern.
- **Framing correction:** this is FULL SOFTWARE / a software suite (could stand alone), NOT a small script. The prior session wasted time thinking small. Expect MULTIPLE sessions. HUGE but achievable.
- The loop: use the FULL pattern (every step, no summarising/faking), render, LOOK (Claude vision) + iterate + self-critique + AUDIT (verify every stitch + instruction was used) BEFORE presenting the side-by-side. Don't iterate on a bad model — if 2.5D isn't reaching customer quality after a fair build, rethink + tell Rebecca, don't nudge.
- Canonical handoff lives in the repo: `apps/web/src/lib/loom/WORKER_BRIEF.md` (the non-negotiable rules + what works/doesn't from the crochet session). The crochet rules still hold; the 3D-Blender RENDER tech does not carry to embroidery.
